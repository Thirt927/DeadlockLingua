# 从零做同一个效果：四种架构与一条研究路线

> 问题：如果抛开现有实现，从零做一个「聊天里能看中文、发消息能发英文」的 mod，有没有更好的办法？
> 先给结论：**有，但取决于一个前提问题——译文是否必须出现在游戏自己的聊天记录里。**
> 答案不同，最优架构完全不同。

---

## 0. 把"效果"拆成三个硬需求

| 需求 | 说明 |
| --- | --- |
| 看得见 | 中文要出现在屏幕上（最好是聊天行下方/上方） |
| 有来源 | 中文文本必须从某处进入游戏进程（本地文件 / 网络 / 内存） |
| 不被封 | 不触发反作弊、不破坏别人游戏 |

10/1 之后，「有来源」只剩四条合法路径：

1. **Panorama JS API** —— 已死（`AsyncWebRequest` / CEF 都没了）；
2. **资源加载** —— 1 bit/次，就是现在的 BTIPC 位信道；
3. **引擎自己的本地化管线** —— 免费、无限带宽，但只能用于**固定字符串**（快捷聊天、Ping、系统提示）；
4. **本机内存（原生 DLL）** —— 无限带宽、零延迟，但踩反作弊。

> 关键判断：**"译文出现在聊天记录里"这个要求，才是逼出位信道的唯一原因。**
> 一旦允许"译文画在聊天区域上方"，第 2 条就完全不需要了。

---

## 1. 决策树

```
译文必须进游戏自己的聊天记录（可滚动、随聊天历史）吗？
│
├─ 不需要 → 架构 A：外置渲染（overlay + 布局回传）
│            端到端 ≈ 1s，零位信道，最稳、最快落地
│
└─ 需要
   ├─ 能接受 DLL 注入 / 封号风险？ → 架构 B：原生 mod
   │      恢复 v1.0 的直连架构（WinHTTP），译文直接塞进 UI，≈0.7s
   │
   └─ 不能 → 架构 C：BTIPC（现状）
          唯一合规方案，代价就是 16 B/s；再叠加"语义路由"提速
```

另有两块**与上面正交**的东西，任何架构都该做：
**D. 内容优先**（本地化覆盖 + 语料表）和 **E. 引擎入口考古**（可能一票否决上述所有结论）。

---

## 2. 架构 A：外置渲染（overlay + 布局回传）

**原理**：把游戏当黑盒。文字不进游戏，画在游戏窗口上面；但**布局信息从游戏里出来**。

```
游戏内 mod（只干两件事）
  ① pushEntry 时把聊天行发到 console.log（已有，出口是免费的 ≈1KB/s）
     字段：文本 / 发送者 / 行序号 / 行的屏幕矩形 / 聊天面板可见性 / 滚动位置
  ② 出站：把用户输入的中文原样发出（同一通道）

桥（本机）
  翻译 → 结果 + 行矩形 → 给覆盖层

覆盖层（WPF 或 DirectComposition）
  按行矩形把译文画在聊天行下方，鼠标穿透，跟随滚动/淡出/分辨率
```

- **端到端**：tail 0.1s（改成 fs.watch）+ 翻译 0.6~1s + 绘制 ≈ **0.8~1.1s**，比现状快 5 倍；
- **信道**：完全不需要位信道，也就没有 T_CLOSE / CRC / 帧 / 16 B/s 这些概念；
- **对齐**：行矩形由 mod 用 `GetPosition`/`GetSize` 取（Panorama 有这些读接口），随滚动事件更新；
- **出站**：桥译好后写剪贴板 + 可选 `SendInput` 发 Ctrl+V（焦点本来就在输入框）；
  不想碰输入注入就退回"用户自己按 Ctrl+V"（v2.0.x 的做法）。
- **代价**：译文不在聊天记录里（不能往上翻）、全屏/独占模式要处理、多显示器坐标、额外进程。

这条路 v2.0.x 已经走过一半（WPF 悬浮窗 + 字幕胶囊），缺的只是**按行对齐**和**低延迟绘制**。
如果重来，我会直接把它做成主路径，而不是"降级方案"。

**失败模式**：游戏用独占全屏（层叠窗口被盖）；反作弊把 SendInput 当异常（可退回手动粘贴）。

## 3. 架构 B：原生 mod（DLL 注入 / hook）

**原理**：拿回被 Valve 删掉的能力——直接调用 Windows 的 HTTP 栈，把结果写进 UI 字符串。

- 恢复的就是 v1.0 的架构（`WinHTTP` + 写 Label），只是从 JS 搬到 C++：
  **没有位信道、没有带宽限制、没有 T_CLOSE，延迟 = 翻译耗时 ≈0.7s**；
- 还能做 JS 做不到的：读输入框内容做预翻译、按发送者做缓存、甚至替换字体渲染；
- 生态里确实有先例：Deadworks 这类 C++ mod 直接 hook Source 2 内部
  （[他们的博客](https://deadworks.net/blog/we-ship-our-ui-through-a-subtitle-system) 明确说"不做 DLL 注入"，
  说明这条路技术上存在、但连老手都刻意避开）。

**代价**：
- 反作弊（City Never Sleeps 明写 "Improved anti-cheat"）→ **封号风险**，不是技术风险；
- 每次游戏更新都要重找签名/偏移，维护成本是现在的 5~10 倍；
- 分发要加载器（ASI/MelonLoader 式），Proton/Steam Deck 另说；
- 出问题就是"游戏崩/被封"，不像 Panorama 最多"mod 不生效"。

**结论**：只有"必须内嵌聊天记录 + 完全不能接受 16 B/s"时才值得，且要接受账号风险。

---

## 4. 架构 C：BTIPC（现状）+ 语义路由

就是现在这套。**它是唯一"合规 + 内嵌聊天记录"的方案**，代价是带宽。
在这个前提下，真正的提速不是改协议，而是**别让每句话都走信道**（见 `translation-rethink.md`）：

- 固定句（快捷聊天/Ping）→ 本地化覆盖或本地语料，**0 字节**；
- 半固定句（推中/撤退/gg）→ 意图码，**1 帧**；
- 自由聊天 → 全文，N 帧。

---

## 5. 正交项 D：内容优先（任何架构都该做，0 成本）

引擎的**本地化管线**是一条被忽视的免费通道：

- 快捷聊天、Ping、系统提示（击杀/目标）都是**客户端本地化**的固定字符串
  （现有代码里 `kind=quick` 直接跳过翻译，就是因为客户端已经本地化了）；
- 只要在 VPK 里覆盖对应的本地化条目，这些消息**天生就是中文**，0 字节、0 延迟；
- 同样的手法可以让"英雄名/装备名"在英文聊天里自动带中文（替换术语 token）。

这不是"翻译"，是"让游戏本来就会显示的中文显示出来"。覆盖率取决于玩家用多少快捷聊天，
但成本几乎为零，任何架构都该先吃掉这块。

---

## 6. 正交项 E：引擎入口考古（1~2 周，可能一票否决）

在写任何代码前值得系统性验证一遍「有没有比位信道宽得多的入口」。已知线索：

| 线索 | 假设 | 怎么验 | 若成立的收益 |
| --- | --- | --- | --- |
| `-netconport` | Source 2 的远程控制台，可执行命令 | 启动带 `-netconport 27015`，telnet 连上去看有没有命令回显 | 命令通道；若能把参数送进 Panorama 全局函数 → **无限带宽** |
| `script` 命令 | 在 UI 上下文执行 JS | 在控制台试 `script`/`panorama_*`，`find` 列命令 | 直接把译文当参数传进去 |
| `-tools` / `-dev` | 松散文件优先加载 | 往 `citadel/panorama/scripts/` 放一个 `.js`，看是否被加载 | 文件级热重载 → 无限带宽 |
| `$.DbgIsReloadingScript` | 引擎有"脚本正在重载"的状态 | 查这个成员在什么条件下为真；配合文件变更测试 | 说明存在热重载路径 |
| `-condebug` 之外 | 有没有控制台**输入**文件 | 查 `-exec`/`-coninput` 类参数 | 一次性注入，可做启动期握手 |

**注意**：这些都要求改启动参数（现在 `StartDeadlock.bat` 已经在加 `-condebug`，所以不是新负担）。
**kill criteria**：两周内如果没有任何命令能触达 Panorama 全局、也没有松散文件热重载，就放弃 E，
回到 A/C；别为它拖住主线。

## 7. 对照表

| | A 外置渲染 | B 原生注入 | C BTIPC（现状） | D 内容优先 |
| --- | --- | --- | --- | --- |
| 端到端延迟 | **~1s** | **~0.7s** | 5.7s（优化后 2~3s） | **0s** |
| 译文在聊天记录里 | ✗ | ✓ | ✓ | 仅固定句 |
| 反作弊风险 | 低（不注入） | **高** | 无 | 无 |
| 更新后存活率 | 高（只依赖 console.log + 窗口） | 低（每次重做偏移） | 中（依赖 Image 行为） | 高 |
| 实现工作量 | 1~2 周（大半已有） | 1~2 月 + 持续维护 | 已有 | 2~3 天 |
| 多显示器/全屏 | 要处理 | 无差别 | 无差别 | 无差别 |
| 额外进程 | 需要 | 不需要 | 不需要 | 不需要 |

## 8. 如果我从零开始，会这么搭

1. **第 1 周**：D（本地化覆盖 + 最热 2k 句语料）+ A 的 MVP（按行矩形的覆盖层，fs.watch 尾随）。
   目标：开箱就有 0 延迟的固定句 + 1s 的自由聊天，**完全不碰位信道**。
2. **第 2~4 周**：E 的考古（并行）。任何一条成立 → 直接把 A 的覆盖层换成"内嵌 + 宽通道"，
   架构 C 直接退役。
3. 若 E 全灭、且用户明确要"内嵌聊天记录"：**才**回到 C（BTIPC）+ 语义路由；
   把 B 作为"高风险选项"写进文档，让用户自己选。

一句话：**先证明"必须内嵌"，再接受 16 B/s。**
现在这套方案的所有复杂度（16B 帧、CRC、T_CLOSE、风暴模式）都是"内嵌 + 合规"这两个约束的
副产品；如果从零开始，应该先用 1~2 周验证这两个约束能不能被绕开，而不是先把它们当成公理。
