# 重构思路：从「搬文本」到「搬指针」

> 前一份 `btipc-speedup-plan.md` 解决的是「同一套原理下怎么更快」（-35% ~ -60%）。
> 这份回答更本质的问题：**为什么每句话都必须过那条 16 B/s 的管子？**
> 结论：真正的数量级不来自「把管子加粗」，而来自**按"这句话是否已知"分流**——
> 已知的直接在本地渲染（0 字节），半知的只传一个码（1 帧），未知的才传全文（慢路径）。

---

## 1. 先承认物理天花板

已确认（`docs/btipc-v1.md` §1 / `architecture.md` §9）：

- 引擎会自动发起的只有**资源加载**：一次加载 = 一个 `ImageLoaded` = **1 bit**，没有读回通道；
- 本仓库当前实现里,HTML 面板不可用(只测过 http/data/file);文件/剪贴板/convar 无读取原语、命名空间全空；
- 面板数加倍的收益被延迟增长吃掉（256 面板：吞吐 +2.4%、延迟 ×2.2）。

⚠️ **2026-10-24 更正**：「更宽的管子不存在」**不成立**。上游 BabelTower 2026-10-15 实车证实:
受信任的本机自签 https 可让隐藏面板加载页面、由页面同源 fetch 取整条结果,下行 **<1s**。
本仓库(2.1.0)未移植,所以下文的重构仍然有效;但它的定位是「移植前的过渡方案」,不是终局。
现在一条 60B 译文要 6 帧 ≈ 3.9s，其中还有 6B/16B 的帧头开销——
**99% 的传输时间花在"玩家其实早就知道该说什么"的句子上**（推中、撤退、gg、敌人不见了）。
这就是可以重构的地方。

| 路径 | 每句成本 | 60B 句子耗时 |
| --- | --- | --- |
| L0 本地语料/规则命中 | **0 字节，0 帧** | ~0（<50ms 查找） |
| L1 意图码（2~4 字节） | **1 帧** | ~0.65s |
| L2 全文（现状） | 6 帧 | ~3.9s + 等待 |

一句话：**把"平均 6 帧"降到"平均 0.3 帧"，等于把信道提速 20 倍**，而且不用碰协议。

---

## 2. 目标架构：三层路由 + 渐进显示

```
聊天行出现
   │
   ├─ L0 本地匹配（mod 内，0 字节）
   │     · 归一化后精确命中语料表 → 直接注入中文（瞬时）
   │     · 规则/关键词（lane / 动作 / 英雄 / 物品）→ 先插一条「标签条」：
   │         [中] [推] [小心]  ← 0 字节、0 延迟，先给"意思"
   │
   ├─ L1 语义码（桥端分类，1 帧）
   │     · 命中意图：回 1~2 字节 intent + 槽位（英雄 6bit / 分路 2bit）
   │     · mod 用本地中文模板渲染整句
   │
   └─ L2 全文（现状 BTIPC）
         · 自由聊天、长句、低置信度 → 走 provider + 位信道
```

关键点：**L0/L2 可以共存**。L0 先出结果，L2 到了再"升级"那条 Label（或反之：先占位再替换）。
玩家在 0.1s 内看到"意思"，2~4s 内看到"原话"——感知延迟直接消失。

---

## 3. L0：本地语料（收益最大，风险最低）

### 3.1 语料从哪来

开发机上的 `logs/chat/<matchId>.jsonl` 已经存了**成对的原文 + 译文**（不入库、仅本地）。
挖法：

1. 抽取所有 `text`，归一化（小写、去标点、折叠空白、去玩家名/数字）；
2. 按频次排序，人工/模型清洗掉一次性长句；
3. 对高频句做一次性翻译（复用现有 provider + 术语表），人工抽检；
4. 生成 `{归一化原文 → 中文}` 表，打包进 VPK（mod 侧一份，桥端一份用于版本校验）。

估计量级：5k~20k 条 × 约 60 字节 ≈ 0.3~1.2 MB。VPK 放得下；
Panorama 侧建议存成**一个大字符串**（`\n` 分隔），首次使用时 `split` + 建 `Map`，
不要在启动时解析大对象字面量（加载耗时必须实测，超过 ~150ms 就改成按需分段加载）。

### 3.2 命中率才是关键指标

先做**离线统计**再决定投入：
`命中率 = 归一化后能在语料里找到的消息 / 总消息`。
经验上游戏内短句重复率很高，但必须用真实日志算，别拍脑袋。

- 命中率 ≥ 40%：值得做，直接把平均帧数砍掉一半；
- 20%~40%：只做「标签 + 意图」两层，语料只收最热的 2k 条；
- < 20%：放弃语料，把精力放到 L1/协议提速上。

### 3.3 风险

- **过期**：新英雄/新黑话 → 语料表要跟版本走（用现成的 `scripts/sync_heroes.js` 思路做再生成）；
- **错译固化**：一句错译会被复用一万次 → 必须抽检 + 允许用户"报告错译"（写回桥端一个覆盖表）；
- **体积/加载**：见上，必须实测解析耗时。

## 4. L1：意图码（让"半知"的句子只占 1 帧）

### 4.1 码表设计

```
intent  : 0..255        推中 / 撤退 / 小心 gank / 敌人消失 / 集合 / gg / 夸奖 / 骂人 / 求支援 ...
slot1   : 0..63         英雄（42~46 个 + "自己/对面"）
slot2   : 0..3          分路（上/中/下/野区）
flags   : 1B            时态/否定/紧急度
```

一帧 10B 载荷足够放 3~4 字节的码 + 余量，**1 帧 = 0.65s**（配 UTF-16/瘦帧后可以更低）。

渲染在 mod 侧用本地模板：

```js
TEMPLATES[INTENT.PUSH] = "{hero} 在推 {lane}";  // 槽位来自 L1 码，不是信道
```

### 4.2 分类器放哪：优先"本地规则"，不是 LLM

| 做法 | 延迟 | 成本 | 适用 |
| --- | --- | --- | --- |
| 关键词/正则规则（mod 或桥本地） | **~0ms** | 0 | 覆盖 "push mid" / "gg" / "care top" 这类固定句式 |
| LLM 结构化输出（`{intent,slots,confidence}`） | +0.6~1s | 1 次调用 | 自由表达但语义明确 |

**关键**：规则命中时整条链路 0 次 provider 调用、只 1 帧 → 端到端 ~0.7s，比现状快 8 倍。
LLM 分类只在规则不中时用，且**置信度 < 0.8 就不发码，直接走 L2 全文**——宁可慢，不可译错。

### 4.3 为什么值得

- 收益：绝大多数 callout 都是"意图 + 槽位"，传 3 字节和传 60 字节差 20 倍；
- 风险：**错意图比错措辞更致命**（"推中" vs "撤中"），所以：
  - 只在高置信度启用；
  - 界面上给这类译文一个可识别的小标记（体现"这是概括"）；
  - 保留"始终显示全文"开关。

## 5. 备选重构：把信道整个绕开

### 5.1 叠加层模式（"快模式"）

v2.0.x 已经实现过：WPF 透明窗 + 字幕胶囊，**完全不走位信道**。
端到端 = tail(0.1s) + 翻译(0.6~1s) ≈ **1s**，比现在快 5 倍。

代价：译文不在聊天记录里、不能随聊天滚动、独占全屏会被遮、要额外一个窗口。
定位：作为"我要最快"的可选模式保留（`overlay.enabled` 已有开关），而不是主路径。

### 5.2 本机小模型

桥端跑 llama.cpp + 量化小模型（0.5~1.7B）：

- 好处：去掉云端 RTT，短句可能 0.2~0.5s；离线可用；
- 坏处：安装体积（模型 300MB~1GB）、CPU 上未必比云端快、俚语质量差；
- 结论：**可选组件**，GPU 用户收益明显；默认仍用云端，失败回落。

### 5.3 只译"最新一条"与"摘要优先"

- 突发 5 条时，只译最后 2 条（老的已过时），其余直接丢弃 → 省带宽给有效信息；
- 先发 8~12 字的"要点"（1 帧），全文随后补（流式）：用户 1s 内知道该干嘛。

## 6. 与现有 BTIPC 的关系

**不推翻，改路由**：

```
今天:  每句 → provider → 全文 → 6 帧
明天:  每句 → 分流器 ┬ L0 本地命中   → 0 帧
                     ├ L1 意图码     → 1 帧
                     └ L2 全文       → N 帧（现状）
```

BTIPC 从"唯一通道"降级为"兜底通道"，协议一行不用改；
新增的是**本地两张表**（语料表 + 意图模板表）和一个**分流器**（先规则、后 LLM）。

## 7. 成本 / 收益 / 风险一览

| 项 | 收益 | 成本 | 风险 | 优先级 |
| --- | --- | --- | --- | --- |
| L0 语料（高频句） | 命中即 0 延迟，平均帧数 -40%~-60% | 中（挖日志 + 清洗 + 打包 + 版本化） | 过期、错译固化 | **高** |
| L0 规则标签（先给意思） | 感知延迟 → ~0.1s | 低（一张关键词表） | 标签粗糙、误标 | **高** |
| L1 意图码 | 1 帧 vs 6 帧 | 中高（码表 + 模板 + 分类器 + 校验） | 语义错译 | 中 |
| L2 协议提速（瘦帧/UTF-16/自适应） | 2~2.5× | 中（两侧同步） | 版本不兼容 | 中 |
| 叠加层快模式 | 端到端 ~1s | 已有代码 | UX 割裂 | 中 |
| 本机小模型 | 离线、低 RTT | 高（体积/质量） | 质量 | 低 |

---

## 8. 建议的落地顺序

1. **先算数**（1 天）：用 `logs/chat` 统计①高频句覆盖率②规则可判定的比例③消息长度分布。
   这三个数决定后面做哪层——没有它们，L0/L1 都是空想。
2. **L0 规则标签**（2~3 天）：纯本地，无风险，立刻让"感知延迟"归零。
3. **L0 语料**（1~2 周，取决于清洗量）：先收 2k 条试水，量命中率再扩。
4. **L1 意图码**（2~3 周）：码表 + 模板 + 高精度规则；LLM 分类只在低风险场景开。
5. 协议提速与叠加层并行推进（见 `btipc-speedup-plan.md`）。

**验收指标**（别只看平均）：

- 端到端 P50 / P95（现状 60B ≈ 5.7s / 更长）；
- L0 命中率、L1 误判率（人工抽检 200 条）；
- 每条消息的平均帧数（目标：从 6 降到 ≤2）；
- "玩家在 1s 内看到有用信息"的比例（感知指标）。

> 一句话总结：**别再把"翻译"理解成"把一句中文搬进游戏"，把它理解成"让玩家尽快知道对方什么意思"**——
> 那么本地能算的就地算（0 字节），能编码的就编码（1 帧），实在不行才搬全文。
