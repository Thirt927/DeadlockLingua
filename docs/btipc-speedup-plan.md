# BTIPC 提速方案：瓶颈拆解与可选机制

> **状态（2026-10-24）**：Phase 1（A1 fs.watch / A2 首拍 300ms / A3 BUSY 180ms / A4 keep-alive /
> 阶段计时）已落地在 `main`，见 `CHANGELOG.md` Unreleased。A5 术语表裁剪、A6 入站占位与 B/C 类未做。

> 目标：回答「还能不能更快、怎么快」。
> 现状基线：v2.1.0（2026-10-16），128 面板 / 16B 帧 / T_CLOSE 600ms / 有效载荷 10B/帧 ≈ **16 B/s**。
> 标 **[实测]** 的数字来自 `docs/btipc-v1.md` §9/§10 与实车日志；标 **[估算]** 的是本方案推算，
> 落地前必须用模拟器 + 实车 dt 采样复测。

---

## 1. 一条 60 字节译文的延迟预算（现状）

60 字节中文 ≈ 20 个字。端到端拆开：

| 阶段 | 耗时 [实测/估算] | 说明 |
| --- | --- | --- |
| 扫聊天行 | 0.2s（最坏 0.8s） | 扫描循环两档 0.2s / 0.8s |
| 写 `console.log` → 桥读到 REQ | 0 ~ 0.8s [实测] | `overlay.js` `POLL_MS = 800` 轮询 |
| 等首拍 | 1.2s [实测常量] | `INITIAL_SHOT_DELAY_MS`：专门等桥读到 REQ，避免首轮全 404 触风暴 |
| 翻译 | 0.6 ~ 1.0s [实测] | DeepSeek 关思考；回退 Bing 会再慢 |
| 传 6 帧 | 6 × 0.65s ≈ 3.9s | 10B/帧，T_CLOSE 600 + SHOT ~50ms |
| 拼装 + 注入 Label | ~0 | 可忽略 |
| **合计** | **≈ 5.5 ~ 5.9s** | 其中**信道占 ~66%** |

结论：**先砍等待（tail / 首拍 / BUSY），再砍帧数（编码 / 帧头），最后才碰物理位率**。

## 2. 瓶颈排序

1. **零位无法主动告知** —— 这是 BTIPC 的根本约束：位=1 有 `ImageLoaded`，位=0 只能靠「等到超时」。
   所以每轮必须等满 `T_CLOSE`，吞吐 = 128 bit / T_CLOSE，跟内容无关。
2. **每帧 10B 有效载荷 / 16B 帧** —— 62.5% 效率，是纯协议开销。
3. **中文 3 字节/字** —— 传输的是字节，不是字符；换编码直接省 1/3。
4. **每轮固定 600ms** —— 位延迟 P50 31ms / P95 161ms / Max 522ms，600ms 是按 Max 定的保守值。
5. **串行 + 每消息一次 1.2s 首拍** —— 突发 3 条消息就多付 2.4s 等待。
6. **翻译服务 0.6~1s** —— 与信道同量级，不能忽略（keep-alive / 提示词裁剪各能省 0.1~0.3s）。

## 3. A 类：不改协议就能拿到的收益（低风险，优先做）

| # | 改动 | 机制 | 预估收益 [估算] | 风险 |
| --- | --- | --- | --- | --- |
| A1 | `fs.watch` + 100ms 增量 tail 替代 800ms 轮询 | `console.log` 一有追加就读；保留指纹检测日志重写 | **-0.6 ~ -0.8s / 条** | 低（要处理 rename/截断重开、半行 tail） |
| A2 | `INITIAL_SHOT_DELAY` 1200 → 300ms | 尾随变快后不必等 1.2s；首轮若 BUSY 也只是 1 轮开销 | **-0.9s / 条** | 低（与 A1 绑定；A1 不做则会把 BUSY 率抬高三倍，反而更慢） |
| A3 | BUSY 退避 500 → 150~200ms | 翻译没好在等，不该按「一整轮」的节奏退让 | **-0.3 ~ -0.6s / 条** | 低（改一个常量 + 回归测试） |
| A4 | 服务商 keep-alive Agent | `openai.js` 目前每次 `https.request` 新建 TLS；Bing 已有 `keepAlive` | **-0.1 ~ -0.2s / 条** | 低 |
| A5 | 术语表按需注入 | `glossary.buildHint()` 固定 ~6k 字符（≈2k token）每次都塞；改成只挑原文里出现的英雄/装备名 | -0.1 ~ -0.3s + 降本 | 低-中（要保证不漏词，宁可多留几项） |
| A6 | 入站即时占位 | 派发时先在行下插一条灰色「译文中…」，完成再替换 | 感知 -2~4s | 低（注意别和错误标签/去重冲突） |
| A7 | 队列优先级 + 过期丢弃 | 突发消息里只译最新的 N 条；超过 10s 未开始的老消息直接放弃 | 省带宽，最新这条更快 | 低-中（策略可配） |

> A1+A2+A3 合计约 **-1.8 ~ -2.3s**：60B 从 ~5.7s 降到 **~3.6s**，不动协议、不动游戏侧状态机。

## 4. B 类：协议 v1.1（收益最大，需要两侧同步改）

现状规格里已经留了「v1.1：精确闭合 + 紧缩帧」的口子（`docs/btipc-v1.md` §10），下面给具体化。

### B1. 瘦帧：帧头 6B → 4B（payload 10 → 12B，**+20%**）

```
现状:  B0 seq/END | B1..B2 request_id | B3 VALID/LEN | B4..B5 CRC16 | payload 10B
提议:  B0 seq/END | B1 VALID/LEN     | B2..B3 CRC16 | payload 12B
```

`request_id` 其实冗余：窗口号 `w` 已经在 URL 里，桥端按 `w` 取帧，串窗的前提是桥自己有 bug。
保留 `w` 校验即可；若要保险，把 id 放进**每窗首帧**（seq=0）的附加字节，其余帧省掉。

- 收益：60B 从 6 帧 → 5 帧（-0.65s）；配合 B2 更明显。
- 代价：CRC 覆盖范围与位序变了，`crc16`/`framer`/游戏侧内联副本/全部测试要同步改，协议版本号必须升。

### B2. 编码：中文按 UTF-16LE，或走 12-bit 静态字表

| 方案 | 60B（20 字）变 | 帧数(12B payload) | 复杂度 |
| --- | --- | --- | --- |
| 现状 UTF-8 | 60B | 5 | — |
| UTF-16LE（CJK 优先，ASCII 段仍 UTF-8，1 字节 codec 标记） | 41B | 4 | 低（两侧各 20 行） |
| 12-bit 字表（约 3000 常用汉字） | 31B | 3 | 中（两侧同一张表 + OOV 转义） |

> 目标语言是中文时 UTF-16LE 几乎稳赚；字表再快 25%，但要维护「表版本」，且 OOV（生僻字、英文名）
> 要能回退，收益/风险比不如 UTF-16LE 干净。建议先做 UTF-16LE，字表作为可选项。

### B3. 闭合窗口自适应（替代写死 600ms）

- 常态 `T_CLOSE = 400~450ms`（覆盖 P99 左右），失败即重投；
- 连续失败 → 按现有**风暴模式**抬到 2.5s，恢复后逐步回落（±50ms 的慢启动）；
- 每帧已记 `dt`，桥端可从 `BTIPC: r=.. dt=..` 行统计真实分布，把窗口定在 P99.5 + 30ms。
- 收益 [估算]：-15%~-20% 帧时间；风险：位延迟长尾（进图/卡顿）会触发重投，**净收益必须实测**，
  别拍脑袋调到 300ms —— 128 bit 里只要有 1 bit 迟到，整帧 CRC 就废，重投一轮反而更贵。

### B4. BUSY 专用短轮询

现在 BUSY 也走「一整轮 600ms + 退避 500ms」。改成 BUSY 时用 150ms 小间隔连问（只读 VALID 位，
不需要完整 128 bit），翻译一好立刻切数据轮。收益与 A3 同源，但更彻底。

### B5. 批量窗口（突发消息）

一个 REQ 带 N 条文本（`op=batch\n[{...},{...}]`），桥一次 provider 调用译完，编成**一个**窗口：

```
payload = [itemCount][len_i][text_i]...
```

- 省掉 (N-1) × (tail 等待 + 首拍 + BUSY + 收尾)，字节数不变；
- 3 条突发：串行 ~17s → 批量 ~13.5s（差的是每条的固定开销），且第 3 条不再等前两条。
- 代价：游戏侧要按 item 边界拆帧、分别注入各行；错误粒度变成「整批失败」→ 需要逐条降级。

### B6. 边译边发（流式）

provider 流式返回时，桥每攒够 10~12 字节就先发一帧（`CONT` 位），游戏边收边更新 Label。
省掉「翻译完才开始传」的 ~0.6~1s 串行，但需要协议支持「未完成」语义，且首帧可能只有半句。
收益 [估算] -0.3~-0.8s，复杂度中高，放在最后。

## 5. C 类：换机制（v2，收益大但要重做状态机）

### C1. 差分双面板：让「0」也主动上报

零位之所以贵，是因为「没有事件」。用**两个面板表示 1 bit**：

```
bit=1 → 面板 A 的 URL (200 PNG)
bit=0 → 面板 B 的 URL (200 PNG)
```

两边都会 fire，于是每位在**到达时**就确定了，不用等超时：

- 128 面板 = 64 bit/帧（8B 载荷），帧时间 = 最大到达延迟（典型 160~300ms，长尾 500ms），
  不再固定 600ms；
- 没有「零位超时」，也就不需要 T_CLOSE 猜；CRC 失败只可能是丢事件，重投更精准；
- 代价：位密度减半。8B/0.35s ≈ **23 B/s**，比现在 16 B/s 只快 ~1.4× —— 除非叠 C2。

### C2. 逐面板流水线（真正的数量级提升）

现在 128 个面板在同一条 600ms 时间线上「齐步走」，快面板要等慢面板。改成**每个面板各自循环**：

```
面板 p: 请求 (w, seq=p 的当前帧号) → 等 fire/超时 → 立刻请求下一帧的第 p 位
```

- 配合 C1（正 0），每个面板的节奏由自己的 RTT 决定（P50 ~31ms），不再被最慢的 1 bit 拖住；
- 帧不再有全局边界，桥端按「每面板每帧」发位，游戏侧按 (panel, frame) 收集；
- 理论吞吐：128 面板 × 1 bit / ~0.1~0.2s ≈ **640~1280 bit/s**；差分方案位密度减半，折合有效载荷
  **40~80 B/s**，是现在的 2.5~5 倍（不是 10 倍 —— 帧头占比会跟着变差）；
- 代价：协议 v2（每面板序号 + 窗口内乱序重组）、状态机整体重写、`ImageLoaded` 事件量 ×2、
  桥端要按面板维护位游标。**必须先在模拟器里验证**，不能直接上实车。

### C3. 多端口 / 多主机名分片（先测量再决定）

如果引擎的图片加载器对「同一 origin 的并发连接」有上限（Chromium 是 6），128 个请求会排队。
分片到 `127.0.0.1:8791..8794`（或 `127.0.0.1` / `127.0.0.2` / `[::1]`）即可绕过：

- 成本：桥多监听 3 个端口，URL 按 `p % 4` 选端口；
- 是否需要：看 `dt` 分布 —— 若 P50 只有 31ms，说明没排队；若 dt 集中在 ~600ms 且与并发相关，再上。
- 风险：低（图片加载不做 CORS 检查），但要确认引擎不把不同端口的图当同一资源缓存。

### C4. 面板数 128 → 192？（不建议，除非实测翻案）

上游实测 256 面板是「吞吐 +2.4%、延迟 ×2.2」，基本白给。192 没测过，但趋势明确：
位率提升被延迟增长吃掉。**保持 128**，把精力放在编码/帧头/流水线上。

### C5. 其它引擎入口能不能更快？

**在本通道内部**:没有更快的物理入口 —— 引擎会自动发起的只有资源加载(Image / 字体 / 音频),
全是 1 bit 粒度;`<HTML>` 面板在本仓库当前实现下不可用;文件/剪贴板/convar 无读取原语。
所以对 BTIPC 只能优化「每 bit 多贵」。

⚠️ **2026-10-24 更正(本计划前提之一作废)**:上面"`<HTML>`/CEF 已死"只是**对 http/data/file
三种 scheme 的观测**,不是引擎能力。上游 BabelTower 2026-10-15 实车证实:受信任的本机自签
https 可让隐藏面板加载页面、由页面同源 fetch 取整条结果,下行 **<1s** —— **存在更宽的管子**,
只是本仓库还没修。因此:继续在 BTIPC 上做微调的收益上限,低于"先把这条面板通道移植进来"。
见 `docs/architecture.md` §10、上游 https://github.com/c1375rick/BabelTower/blob/main/docs/btipc-https-v1.md。

## 6. D 类：感知层（不加速度，但让用户觉得快）

| # | 做法 | 效果 |
| --- | --- | --- |
| D1 | **边打字边预翻译**（出站） | 读 `ChatInput.text`，停顿 700ms 且长度 ≥2 时先发一次 `tag=prefetch` 请求；回车时若文本一致直接取结果/等已在途的 → 出站从 3~6s 降到 ~0.3~1s。代价：打废的句子会白花 provider 调用（可限流/取消）。**这是出站最大的体验提升**，且不动声道。 |
| D2 | 回车即显示「翻译中…约 2 秒」+ 进度点 | 已有 hint，可再加剩余帧数估计 |
| D3 | 入站占位（A6） | 同上 |
| D4 | 常用语本地化：快捷聊天/Ping 由客户端本地化，跳过；固定短语走本地词表 | 零延迟 |

## 7. 不建议做

- **压缩（gzip/zlib）**：60B 级文本压缩头比收益大，还多一层两侧同步的解码器。
- **把诊断/日志/整份配置塞进信道**：已经踩过（`op=config` 1313B > 128 帧上限；health 每 5s 吃掉六成带宽）。
- **靠「位到达时间差」编码**：规格里明令禁止（跨版本不稳定）。
- **无脑调小 T_CLOSE 到 250ms**：128 bit 里 1 bit 迟到就整帧废，重投成本 > 省下的时间。
- **多窗口并行抢同一批面板**：单槽设计是有意的，抢起来会互相 `supersede`。

## 8. 组合目标（估算，落地后以实测为准）

一条 60B 译文：

| 阶段 | 现状 | Phase 1（A 类） | Phase 2（A + B1/B2/B3） | Phase 3（+ C1/C2） |
| --- | --- | --- | --- | --- |
| 等待（tail/首拍/BUSY） | ~1.8s | ~0.4s | ~0.4s | ~0.2s |
| 翻译 | 0.8s | 0.7s | 0.7s | 0.7s |
| 信道 | 3.9s | 3.9s | ~1.6s（4 帧 × 400ms） | ~0.8s（流水线，按 40~80 B/s 估） |
| **合计** | **≈ 5.7s** | **≈ 3.6s** | **≈ 2.7s** | **≈ 1.7s** |

- 只做 A 类就能拿到最大性价比（约 **-35%**，且不动协议）；
- B 类是「规格 v1.1」的兑现，目标是 60B ≤2.5s；
- C 类才有数量级变化，但属于重写，先模拟器验证。

出站（发送前翻译）另有 D1：感知延迟可以从 3~6s 压到 1s 内。

## 9. 实施顺序与验证

1. **先测量**：在现有 `dt` 日志基础上补「REQ 发出时刻 / 桥读到时刻 / 翻译完成时刻 / 末帧时刻」四个时间戳，
   跑 20 条 60B 文本，拿真实分布。没有这组数，任何 T_CLOSE 调整都是猜。
2. **A1~A4 + A6**（1 天内可完成，低风险）→ 实车 A/B。
3. **B1/B2/B3**（协议 v1.1，两侧同步 + 全量测试）→ 用模拟器先跑通，再实车。
4. **D1**（预翻译）可与 3 并行，因为它只动业务层。
5. **C1/C2** 立项前先做「60 分钟模拟器压测」：把真实 dt 分布喂进去，比对 128/256 面板、600/400ms、
   差分/非差分的吞吐-延迟曲线，再决定是否值得重写。

> 铁律不变：改 BTIPC 任一侧必须同步另一侧 + 跑 `tests/btipc/*` 与 `scripts/lingua_chat_simtest.js`；
> 协议版本要能在 REQ 行里协商（`v=1` / `v=1.1`），否则「新桥 + 旧 mod」会互相读不懂位。
